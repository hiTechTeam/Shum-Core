# Shum Core

Общее ядро Shum на Rust и CLI-клиент `shum`. Контракт совместимости:
работающее iOS-приложение 1.0 и примеры из [Shum-Protocol](https://github.com/hiTechTeam/Shum-Protocol).

## Состояние

Ядро v1 и хранилище готовы (этапы 0–3). CLI теперь запускается: есть
интернет-переписка через Nostr, push-запросы, команды, несколько профилей и
TUI с аватарами и QR. Это рабочая реализация этапов 4–5 для проверки.
Полная приёмка интернет-переписки с настоящим iPhone ещё **не выполнена**.

На macOS подключён Bluetooth/GATT: поиск через btleplug, объявление своего
профиля через CoreBluetooth, Noise XX, карточки рядом и доставка Shum-пакетов.
На настоящем iPhone подтверждены взаимное обнаружение, принятие приглашения,
сообщения в обе стороны и отметка прочтения от телефона. Интернет-доставка
у тестового CLI была отключена: обмен прошёл через Bluetooth.
Этап 6 ещё не завершён: Linux/Windows пока имеют только central-адаптер,
без GATT-сервера; фото-аватары не реализованы. Текущий iPhone игнорирует
пакеты фото, см. вопрос 1 в `protocol/spec/04-packets.md`.
`link`, `unlink` и `sync` (этап 7) отсутствуют. Протокол v2 нельзя
реализовывать до согласования черновика с владельцем.

  отдельной службы SCM пока нет.

| Crate | Ответственность |
|---|---|
| `shum-core` | Байты и события на входе, действия на выходе; без ввода-вывода |
| `shum-transport-nostr` | Релеи, подписки и доставка Nostr |
| `shum-transport-ble` | Поиск, объявления, GATT, Noise и сетка Bitchat |
| `shum-store` | Совместимая с iOS SQLite-база, шифрование и ключи профилей |
| `shum-cli` | Команды, TUI, выбор профиля и системная служба |

`protocol/` закрепляет конкретный коммит спецификации через git submodule.
Интерфейс UniFFI предусмотрен отдельной feature `uniffi` и типами сборки
`staticlib`/`cdylib`; начальные привязки уже компилируются, API состояния будет дополняться при подключении клиентов.
Ядро получает время и случайные байты от клиента, само их не запрашивает.

Аватары, QR, цвета, форматирование терминала и окна относятся к клиентам.
Генератор пикселей v1 и его Swift-тесты находятся в `shum-cli::avatar`.
Ядро знает только подписываемые поля seed/version/hash/size и проверяет их
протокольный смысл. Декодирование изображений и подготовка фото также
принадлежат клиенту. Это уточнение заменяет первоначальное размещение
генератора аватаров в ядре.

Для ключей выбраны `ed25519-dalek` 2.2, `x25519-dalek` 2.0 и `secp256k1`
0.31 (libsecp256k1: BIP-340 и доступ к исходной ECDH-точке). Dalek даёт
явную строгую проверку, X25519 использует фиксированные ключи от вызывающей
стороны. `Secret32` не реализует Debug/Serialize и очищается через zeroize;
это не обещание очистки всех копий внутри внешних библиотек.
ChaCha20-Poly1305, SHA-256/HMAC/HKDF используют RustCrypto. Версии закреплены
в Cargo.lock, byte-level совместимость проверяется примерами Swift.

Canonical JSON написан отдельно, serde используется для разбора и моделей.
Графемы считает unicode-segmentation, NFC для BLE-профилей выполняет
unicode-normalization. Пример API транзакций: [docs/core-api.md](docs/core-api.md).
Набор Foundation-пробелов зафиксирован в `card.rs`
и проверен Swift-примером всех 26 scalar. Вопрос о строгом отклонении
вырожденных Ed25519-подписей и о replay-ошибке Swift записан в спецификации;
оба исключения совместимости согласованы владельцем 8 октября 2026.

DEFLATE использует flate2 с backend zlib: поток zlib-rs отличается от Apple
Compression и меняет signing bytes. Точные потоки и подписи проверены на
macOS; межплатформенная проверка остаётся частью отключённого CI.

Feature `uniffi` включает настоящий scaffolding и начальные функции для
Swift/Kotlin: проверка карточки, разбор приглашения, canonical packet и
открытие envelope. `cargo check -p shum-core --features uniffi` проходит.
Полный API состояния ещё формируется; xcframework и iOS-приложение не меняются.
[UniFFI](https://mozilla.github.io/uniffi-rs/latest/proc_macro/index.html),
[строгая Ed25519-проверка](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/struct.VerifyingKey.html).

Хранилище, миграция, блокировки и команды проверки: [docs/storage.md](docs/storage.md).
Проверки Linux/Windows ещё не выполнены.

## Установка готового CLI

Для macOS добавлена локальная сборка установщика `.pkg` и пакета Homebrew.
Установщик добавляет команду `shum` в `/usr/local/bin`. Профили и переписка сохраняются.
Пакеты ещё не опубликованы. Подготовка выпуска, проверка и ограничения описаны
в [docs/distribution.md](docs/distribution.md).

## Получение исходников и проверка

Оба репозитория приватные, для клонирования нужен доступ к ним:

```sh
git clone --recurse-submodules https://github.com/hiTechTeam/Shum-Core.git
cd Shum-Core
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo fmt --all -- --check
```

Для уже клонированного репозитория: `git submodule update --init --recursive`.

На этом Mac rustup установлен через Homebrew. Его команды доступны после:

```sh
export PATH="/opt/homebrew/opt/rustup/bin:$PATH"
rustc --version
cargo --version
```

Это меняет PATH только в текущем терминале; настройки shell автоматически
не редактируются.

Установка клиента:

```sh
cargo install --path crates/shum-cli --locked
```

На этом Mac установленный бинарник доступен по `~/.cargo/bin/shum`.
Чтобы команды `shum`, `shum chats` и остальные находились в новых вкладках
Terminal и Warp, добавьте в `~/.zshrc`:

```sh
if [[ -d "$HOME/.cargo/bin" && ":$PATH:" != *":$HOME/.cargo/bin:"* ]]; then
  export PATH="$HOME/.cargo/bin:$PATH"
fi
```

Затем откройте новую вкладку терминала. Для уже открытой вкладки достаточно:

```sh
export PATH="$HOME/.cargo/bin:$PATH"
rehash
shum chats
```

`zsh: command not found: shum` означает, что shell не нашёл бинарник в PATH.
Проверить путь можно командой `command -v shum`.

Можно обойтись без изменения PATH:

```sh
~/.cargo/bin/shum init
~/.cargo/bin/shum
```

Первый `shum` сам откроет создание профиля, если профилей ещё нет.
`shum init` открывает тот же мастер: имя, прозрачный пиксельный аватар
(`r` другой, Enter подтвердить), сохранение ключей и проверка чтения
зашифрованной базы. Esc до подтверждения отменяет создание без записи профиля.
`init --name <имя>` остаётся неинтерактивной командой. Для сервера без
него: `shum init --name server --headless` (Unix, ключи в файле 0600).
При закрытии TUI служба продолжает принимать сообщения; остановить её:
`shum daemon --stop`. Для автозапуска после входа: `shum daemon --install`.

Каталог данных macOS: `~/Library/Application Support/org.Shum.Shum`.
Точный путь показывает `shum status`. Для отдельного теста:
`shum --data-dir /tmp/shum-demo init --name Test --headless`.
Все команды принимают `-p <имя или ID>`, `--json`, `--ascii` и `--data-dir`.
Вне терминала TUI не открывается; `open --json` выдаёт обновления сообщений
построчно до Ctrl+C. Ники с пробелами нужно заключать в кавычки.

Terminal.app автоматически использует палитру 256 цветов. Цветной TUI задаёт
фон и цвет текста явно, поэтому остаётся читаемым и в светлой теме терминала.
Warp, iTerm2 и WezTerm получают пиксельные аватары как PNG; Kitty использует
свой графический протокол. При выводе символами `▀▄` миниатюры в списках
показывают лицо крупнее, без уменьшения до сетки 6×6. В открытом чате и мастере
создания профиля доступен полный портрет; прозрачные пиксели сохраняют фон UI.
В режиме `--ascii` аватары и цвета по-прежнему отключены.

Обычные команды тоже используют цвета из макетов: `shum chats` выделяет
людей рядом и непрочитанные сообщения зелёным, приглашения жёлтым,
подсказки команд голубым. `shum about` показывает пиксельный логотип,
сведения о системе и образцы палитры. В Terminal.app используется 256 цветов,
в Warp — RGB. Команды сохраняют фон терминала и сбрасывают цвет после вывода.
При перенаправлении в файл, с `--json`, `--ascii`, `NO_COLOR=1` или `TERM=dumb`
цветовых кодов в выводе команд нет.

Проверка цветного вывода в PTY с временным профилем и локальной подставной
службой (без Keychain, Bluetooth и внешних релеев):

```sh
python3 crates/shum-cli/tests/manual/command_colors.py ~/.cargo/bin/shum
```

Bluetooth включён по умолчанию у обычных профилей. `init --headless`
создаёт профиль с выключенным Bluetooth; включить его явно можно командой
`shum --bluetooth status`, выключить: `shum --no-bluetooth status`.
Оба флага сохраняют настройку выбранного профиля. На macOS разрешите доступ
к Bluetooth приложению **Shum** в системном запросе. Служба запускается через
Launch Services как фоновое приложение с собственным описанием доступа
(`NSBluetoothAlwaysUsageDescription`). Поэтому разрешение относится к Shum,
а запуск CLI не зависит от наличия этого описания у Warp или другого терминала.
Если ранее отказали: «Системные настройки → Конфиденциальность и безопасность
→ Bluetooth → Shum», затем `shum --bluetooth status`.
Без адаптера интернет-переписка продолжает работать.
По Bluetooth показывается только профиль, выбранный через `profile use`;
фоновые службы остальных профилей продолжают работу через релей.
После обновления бинарника перезапустите старую службу: `shum daemon --stop`,
затем `shum`. Первое обнаружение занимает несколько секунд; вкладка «Рядом»
обновляется автоматически. Расстояние приблизительное, по RSSI; если сигнал
недоступен в текущей роли GATT, число не показывается.

Для сборки Bluetooth на macOS нужны Xcode Command Line Tools (`xcrun swiftc`).
Небольшой встроенный Swift-процесс выполняет только CoreBluetooth I/O;
ключи, проверка личности, шифрование и сообщения остаются в Rust.
Подписанная локально копия службы хранится в `services/<hash>/Shum.app`
в каталоге данных. Копия создаётся при первом запуске каждой сборки;
работающие версии не перезаписываются, чтобы не ломать проверку подписи macOS.
При первом запуске macOS также может запросить доступ Shum к сохранённым
ключам профиля. CLI ждёт запуска службы до минуты. Локальная подпись не
заменяет Developer ID: после пересборки macOS может снова запросить доступ.
Автозапуск при входе по-прежнему включается только через `daemon --install`.
Проверка запуска macOS на двух временных профилях без Bluetooth и интернета:
`python3 crates/shum-cli/tests/manual/macos_app.py target/release/shum`.

### Команды

```sh
shum profile
shum profile list
shum profile use "Работа"
shum profile name "Новое имя"
shum profile bio "О себе"
shum profile avatar --random
shum invite
shum add 'shum://c4/…'
shum add --image ~/Desktop/invite.png
shum contacts
shum invite "Аня"
shum accept "Аня"
shum chats --invites
shum chats --unread
shum send "Аня" "Привет"
shum open "Аня"
shum ui "Аня"
shum keys verify "Аня"
shum keys verify "Аня" --qr
shum react <ID-сообщения> like
shum clear "Аня" --confirm
shum lock
shum unlock
shum status --json
```

`add` сохраняет карточку. `invite <ник>` отправляет запрос на чат; `send`
доступен после принятия. Подтверждение команды отправки означает запись
в зашифрованную очередь. `forwarding` означает принятие релеем, `delivered`
и `read` появляются только по подписанному ACK собеседника.
Реакции v1: `heart`, `like`, `dislike`, `laugh`, `fire`, `coffin`, `hundred`, `horror`.

В TUI: 1–4 фильтры, стрелки или j/k для списка, Enter открыть/отправить,
Tab список/ввод, Esc из поля к списку, PgUp/PgDn история, Ctrl+P профили,
Ctrl+N рядом, i мой QR, a добавить, q выйти из списка. Клавиши i/q/a/j/k
работают и в русской раскладке. В поле сообщения буквы вводятся как текст.
Ctrl+C, Ctrl+Q и F10 выходят из любого окна TUI, в том числе во время
ожидания c2/службы. Несохранённый текст остаётся при Esc к списку.
Поддерживаются мышь и вставка текста. Командная строка открывается `/` и
всегда видна, `/help` открывает отдельное окно справки.

Примеры внутри TUI: `/invite` мой QR, `/invite "Аня"` приглашение,
`/add <ссылка>`, `/add --image "путь.png"`, `/accept [ник]`, `/decline [ник]`,
`/open "Аня"`, `/send "Аня" "Привет"`, `/read [ник]`, `/clear [ник]`
с подтверждением, `/profile name Новое имя`, `/profile avatar --random`,
`/react <ID> <реакция>`, `/cancel <ID>`, `/block <ник> [--undo]`,
`/status`, `/quit` или `/exit`. Ник с пробелами заключают в кавычки.
Повторная одинаковая реакция снимает её, `cancel` убирает сообщение из очереди.
На маленьком экране QR использует существующий формат c2 и требует,
чтобы служба этого профиля оставалась в сети.

Аватары рисуются в CLI: прозрачный персонаж, графический протокол терминала
или `▀▄`; в ASCII они скрыты. Полный непрозрачный Swift-рендерер остаётся
отдельно для проверки контрактных пикселей.

`lock` останавливает службу и запрещает автоматический запуск до `unlock`.
Это блокировка сеанса, отдельного PIN или пароля CLI пока нет. Ключи
защищает системное хранилище либо права файла. `keys verify` показывает
отпечаток iPhone (12 hex) и полные отпечатки ключей. Общего числового кода
пары из макета в iPhone v1 нет; расхождение записано в spec/02.

Настройки сохраняются в зашифрованной базе профиля:

```sh
shum --relay wss://nostr.oxtr.dev --relay wss://soloco.nl status
shum --push-url off status
```

По умолчанию используются четыре релея из iOS и тот же push API. Не задавайте
`--push-url off`, если нужны уведомления на iPhone. Если Yandex Cloud
блокируется VPN, выключите VPN для проверки; CLI не привязан к `en0`.

Удалять только ненужный профиль, подтверждая его имя:
`shum profile delete Test --confirm Test`. Имя должно совпасть точно.

## CI

GitHub Actions настроен на ручной запуск (`workflow_dispatch`) по просьбе
пользователя. Push и pull request автоматически CI не запускают. Для ручного запуска сначала нужно включить workflow в GitHub Actions.
Ручная проверка выполняет тесты, clippy и форматирование на macOS, Linux и Windows.
Стандартный `GITHUB_TOKEN` не открывает другой приватный
репозиторий. Владелец организации разрешил deploy keys. Для Shum-Protocol
настроен отдельный ключ только с правом чтения, его закрытая часть хранится
в Actions secret `PROTOCOL_DEPLOY_KEY` репозитория Shum-Core. CI извлекает
ревизию из gitlink `protocol` и получает именно этот коммит. Без секрета
checkout завершится ошибкой. Закрытый ключ не хранится в исходниках и отчётах.

## Сценарии приёмки

Сценарии 4–5 и Bluetooth на macOS доступны для ручной проверки.
Автоматические результаты указаны выше; полная проверка с настоящим iPhone
остаётся обязательной. Фото и сценарий 7 описывают будущую приёмку.

### Этап 4: интернет и iPhone

1. В CLI выполнить `shum init`, задать имя. Проверить `shum profile`,
   `shum profile list`, `shum status` и их варианты с `--json`/`--ascii`.
2. Выполнить `shum invite`, отсканировать QR на iPhone, сохранить контакт.
   Добавить карточку iPhone через `shum add`, затем отправить
   приглашение командой `shum invite <ник>`.
   Принять на iPhone. Проверить состояния приглашения с обеих сторон.
3. На другом CLI-профиле (`shum init -p second`) выполнить
   `shum add <ссылка-с-iPhone>` или `shum add --image <png>`.
   Отправить приглашение с iPhone, проверить `shum chats --invites`,
   выполнить `shum accept <ник>`. Сохранение контакта само не принимает чат.
4. Выполнить `shum open <ник>`, отправить сообщения в обе стороны.
   Проверить отметки доставки, прочтения, набор текста и реакции;
   при выключенном CLI дождаться доставки после повторного запуска.
5. Сменить имя и пиксельный аватар на iPhone, затем в CLI. Убедиться,
   что контакт получает новые профили, а старые сообщения сохраняют снимки.
6. Очистить чат на iPhone, проверить результат в CLI по правилам v1.
   Сверить `shum keys verify <ник>` с отпечатком в настройках
   безопасности профиля телефона. Очистка в CLI локальная по правилам v1.
7. Проверить `contacts`, фильтры `chats`, переключение профиля, `lock`,
   `daemon --install`, `daemon --stop`. Удаление профиля проверять на
   отдельном тестовом профиле с подтверждением его именем.

### Этап 5: TUI

1. Запустить `shum` в терминале. Сверить с макетами 10 и 11: статус,
   вкладки 1–4, аватары, переписка, ввод, подсказки клавиш.
2. Проверить стрелки, `j`/`k`, Enter, Esc, Tab, PgUp/PgDn, `q`, мышь,
   `Ctrl+P`, `Ctrl+N` и командную строку `/`.
3. Выполнить `shum ui <ник>`, отправить и получить сообщение с iPhone.
   Убедиться, что поступающие сообщения обновляются без потери ввода.
4. Проверить терминал с изображениями, вариант `▀▄`, режим `--ascii`.
   При перенаправлении `shum > output.txt` TUI открываться не должен.

### Этап 6: Bluetooth

1. На macOS включить Bluetooth на компьютере и iPhone, разрешить доступ.
   Открыть Shum на iPhone, выполнить `shum --bluetooth status`, затем
   `shum` и Ctrl+N. Оба устройства должны видеть друг друга. Команда
   `shum nearby --json` показывает состояние радио и найденные карточки.
2. Выполнить `shum invite <ник>` для человека рядом, принять приглашение.
   Выключить интернет на обоих устройствах, оставить Bluetooth.
3. Отправить сообщения в обе стороны, проверить отметки, повторы и
   примерное изменение расстояния при приближении и удалении телефона.
4. **Пока недоступно:** `shum profile avatar --photo <файл>`. Фото должно быть видно
   только рядом. После отключения Bluetooth через релей передаётся
   пиксельный аватар, фотография не отправляется.
5. Проверить отказ в разрешении, Linux без прав, сервер без адаптера.
   Интернет-переписка должна оставаться доступной.

### Этап 7: устройства v2

Перед реализацией требуется согласованный `protocol/spec/v2-devices.md`.
iPhone 1.0 не поддерживает привязку; эту проверку проводят между двумя
компьютерами или двумя независимыми CLI-профилями.

1. Выполнить `shum link`, отсканировать QR вторым клиентом и сверить код.
   У каждого устройства должен оставаться собственный закрытый ключ.
2. Проверить доставку сообщения всем подтверждённым устройствам и
   отсутствие доставки после `shum unlink`.
3. Выполнить `shum sync` по Bluetooth, проверить выбор восстановления
   очищенных локально чатов.
4. Сравнить очистку «здесь» и «на всех устройствах», повторную
   синхронизацию и совместимость обычной переписки с iPhone 1.0.

## Ограничения работ

Протокол v1 не меняется. Код iOS-приложения не редактируется; новые Swift
генераторы добавляются только в `ShumTests/Protocol`. Запуск разрешён только
для этих тестов на симуляторе iPhone 17 Pro
`9374725C-1A19-4568-A06B-AAB02E8DBCD2`. Коммиты в Shum-iOS требуют
отдельного согласия. Установка Rust и любые загрузки, кроме cargo-зависимостей,
требуют согласия пользователя.
