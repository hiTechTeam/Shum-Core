# Граница ядра и клиента

`shum-core` принимает байты, проверенные сведения о транспортном источнике,
время, UUID и ключи. Возвращает состояние и действия, не выполняя их.
Он не запрашивает системные часы, случайность, файлы, сокеты, Bluetooth,
Keychain и пользовательский ввод.

| Ядро | Клиент / адаптер |
|---|---|
| Ключи, подписи, canonical JSON, правила карточки и поля профиля | Получение и защищённое хранение ключей |
| Noise, Nostr crypto, бинарные пакеты и фрагменты | WebSocket, GATT, разрешения ОС, backpressure |
| Приглашения, сообщения, ACK, блокировки, очереди и интервалы | SQLite commit, таймер, выполнение действий и ошибки I/O |
| Подписанные seed/version/hash/size | Пиксели, PNG, фото, QR, цвета, терминал и TUI |

`shum-cli::avatar` в отдельном [Shum-CLI](https://github.com/hiTechTeam/Shum-CLI)
воспроизводит генератор v1 из Swift. Ядро не зависит от
этого модуля. У подписанного вложения `InvitationAvatar::authenticate`
проверяет только подпись, действие и предел байтов. Декодировать изображение,
проверить единственный frame и размер 1…360, затем отображать должен клиент.
Текущий iPhone вложение приглашения игнорирует.

## Транзакция перед отправкой

1. Клиент получает время, UUID и требуемую свежую случайность.
2. Вызывает `Engine::prepare`, передавая операцию с `Context` и подтверждёнными
   источниками. Получает `Transition { state, actions }`.
3. Сохраняет новое состояние атомарно. При ошибке оставляет прежний Engine,
   сообщает локальную ошибку и не выполняет actions.
4. После успешного сохранения заменяет Engine и выполняет actions.
5. Результат Nostr-релея снова фиксирует через tentative state перед
   следующими действиями. `OK` означает forwarding, только signed recipient
   receipt означает delivered/read.

Контекст содержит заимствованные ключи, состояние их не хранит. Открытые
поля моделей пока предназначены для адаптера хранения и миграций. Криптографию
сессионного источника нельзя выводить из JSON sender: Nostr передаёт автора
проверенного seal, BLE передаёт remote static из завершённого XX.
`Peer::authenticated` проверяет соответствие карточки Noise-сессии.

## Операции

- `add_contact` закрепляет карточку; переписка требует accepted.
- `invitation` реализует request/accept/decline и отдельный подписанный outbox.
- `send`, `receive`, `mark_read`, `cancel_sending`, `toggle_reaction` сохраняют
  порядок истории, receipt и tombstones.
- `set_typing`, `presence` дают эфемерные действия; foreground передаёт клиент.
- `update_profile` повышает revision и заполняет профильную очередь.
- `clear_chat` сохраняет контакт и accepted; сетевой clear-control v1 не имеет.
- `block`, `remove_contact`, `retire` отменяют соответствующие очереди.
- `tick` обслуживает сроки и интервалы, возвращая действия в пределах лимитов.

Для завершения клиентского runtime нужны адаптер совместимого SQLite,
проекция истории/метаданных iOS, исполнение действий, обнаружение BLE,
обработка разрешений и сквозные тесты с телефоном. `retire` прекращает новые
действия; клиент перед этим при необходимости отправляет offline-presence и
после фиксации останавливает транспорт и удаляет секреты.

## Примеры и открытые исключения

Тесты core используют Swift-примеры 01–07 для своих wire/crypto/state частей.
Снимок SQLite 09 проверяется на этапе хранилища, HTTP 08 на этапе сетевого
адаптера; RSSI относится к BLE-адаптеру. Аватары 01 проверяются тестами CLI.
Генераторы Swift запускаются только на разрешённом симуляторе.

Ed25519 strict и исправный replay window Noise подготовлены с явными
регрессионными тестами. CryptoKit принимает два вырожденных примера, Rust
их отклоняет; Swift принимает повтор counter 0 после counter 1, Rust
отклоняет. Оба расхождения записаны в «Вопросы» spec/02 и spec/06 и согласованы владельцем 8 октября 2026. Нормальные подписи, XX transcript и ciphertext
совпадают. Это не подтверждает совместимость с настоящим iPhone целиком.
